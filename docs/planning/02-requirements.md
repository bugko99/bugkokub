# 02 — Requirements Analysis
## ระบบรับเรื่องร้องเรียนศูนย์ดำรงธรรมจังหวัดศรีสะเกษ (DCMS)

> **Planning Only** — อ้างอิงจาก `docs/planning/01-system-overview.md`

---

## 1. วัตถุประสงค์ของระบบ

ระบบ DCMS (Damrongdham Center Management System) มีวัตถุประสงค์หลัก 5 ประการ:

1. **ดิจิทัลไลซ์กระบวนการรับเรื่องร้องเรียน** — แทนที่เอกสารกระดาษและสมุดบันทึกด้วยการจัดเก็บข้อมูลในฐานข้อมูลที่ค้นหาและตรวจสอบได้
2. **ควบคุมระยะเวลาดำเนินการ** — ให้ระบบจับเวลาและแจ้งเตือนเพื่อให้แน่ใจว่าทุกเรื่องได้รับการดำเนินการภายในกรอบเวลาที่กำหนด
3. **เพิ่มความโปร่งใสให้ประชาชน** — ให้ประชาชนสามารถตรวจสอบสถานะเรื่องของตนเองได้ตลอดเวลาโดยไม่ต้องติดต่อเจ้าหน้าที่โดยตรง
4. **เพิ่มประสิทธิภาพการส่งต่อ** — บันทึกและติดตามการส่งต่อระหว่างหน่วยงานโดยมีหลักฐานชัดเจน
5. **สนับสนุนการตัดสินใจของผู้บริหาร** — จัดทำ Dashboard และรายงานสรุปสถิติที่อ่านได้ง่าย

## 2. ปัญหาของระบบเดิม

| ปัญหา | ผลกระทบ |
|---|---|
| **บันทึกด้วยมือในสมุดและกระดาษ** | ค้นหายาก ข้อมูลสูญหาย อ่านยาก |
| **ไม่มีระบบติดตามสถานะ** | เจ้าหน้าที่ไม่รู้ว่าเรื่องอยู่ที่ขั้นตอนไหน |
| **การส่งต่อหน่วยงานไม่มีหลักฐาน** | เกิดข้อพิพาทว่าส่งแล้วหรือยัง ใครรับไป |
| **ประชาชนต้องโทรถามสถานะ** | เสียเวลาทั้งประชาชนและเจ้าหน้าที่ |
| **ไม่มีการควบคุมระยะเวลา** | เรื่องค้างนานโดยไม่รู้ตัว ขาด Accountability |
| **ไม่มีรายงานสรุปเป็นระบบ** | ผู้บริหารไม่ทราบภาพรวม ต้องนับเองจากสมุด |
| **ข้อมูลกระจัดกระจาย** | แต่ละแผนกเก็บข้อมูลไม่เชื่อมกัน |
| **รับเรื่องหลายช่องทางแต่ไม่รวมศูนย์** | มาด้วยตนเอง โทรศัพท์ หนังสือ ไม่มีจุดศูนย์รวมเดียว |

## 3. เป้าหมายของระบบใหม่

| เป้าหมาย | ตัวชี้วัดความสำเร็จ (KPI) |
|---|---|
| รับเรื่องแบบหลายช่องทาง รวมศูนย์ใน 1 ระบบ | ช่องทางรับเรื่องทุกช่องทางบันทึกในฐานข้อมูลเดียว |
| ลดเวลาในการค้นหาข้อมูลเรื่องร้องเรียน | ค้นหาเรื่องจากหมายเลขได้ภายใน 3 วินาที |
| ระบบแจ้งเตือนเมื่อเรื่องใกล้ครบกำหนด | เจ้าหน้าที่ได้รับแจ้งเตือนล่วงหน้า 2 วัน |
| ประชาชนตรวจสอบสถานะเองได้ | ลดการโทรสอบถามลง |
| ผู้บริหารเห็น Dashboard แบบ Real-time | ไม่ต้องรอรายงานประจำเดือน |
| ประวัติการส่งต่อบันทึกครบถ้วน | ตรวจสอบย้อนหลังได้ครบทุกขั้นตอน |

## 4. Functional Requirements

### FR-01: การรับเรื่องร้องเรียนหลายช่องทาง
- **FR-01-1** ระบบต้องรองรับการบันทึกเรื่องร้องเรียนที่รับมาจากหลายช่องทาง:
  - **มาด้วยตนเอง (Walk-in):** เจ้าหน้าที่กรอกข้อมูลแทน
  - **โทรศัพท์ (Phone):** เจ้าหน้าที่รับสายและบันทึกข้อมูลแทน
  - **หนังสือ/ไปรษณีย์ (Letter):** เจ้าหน้าที่สแกนและบันทึก
  - **เว็บไซต์ (Online):** ประชาชนกรอกแบบฟอร์มออนไลน์เอง
  - **นำเข้าจากระบบกลาง (Import):** นำข้อมูลเข้าจากระบบภายนอก
- **FR-01-2** ทุกช่องทางต้องระบุ "ช่องทางที่รับ" (Source Channel) ไว้ในข้อมูลเรื่อง
- **FR-01-3** ระบบต้องออกเลขรับเรื่องอัตโนมัติ (Auto-generated Complaint Number) ในรูปแบบมาตรฐาน

### FR-02: การจัดการข้อมูลผู้ร้อง
- **FR-02-1** บันทึกข้อมูลผู้ร้อง: ชื่อ-นามสกุล, เลขบัตรประชาชน, ที่อยู่, เบอร์โทรศัพท์
- **FR-02-2** รองรับกรณีไม่ประสงค์ออกนาม (Anonymous Complaint)
- **FR-02-3** ระบบต้องไม่บังคับให้ประชาชนสร้างบัญชีผู้ใช้เพื่อยื่นเรื่อง

### FR-03: การจำแนกประเภทและความเร่งด่วน
- **FR-03-1** ระบบต้องมีระบบ Category ของเรื่องร้องเรียนที่ผู้ดูแลระบบจัดการได้ (Dynamic Category)
- **FR-03-2** แต่ละเรื่องต้องระบุระดับความเร่งด่วน (Low / Medium / High / Urgent)
- **FR-03-3** ระบบต้องกำหนด SLA (ระยะเวลาดำเนินการสูงสุดเป็นวัน) ตามประเภทเรื่อง
- **FR-03-4** ระบบแนะนำหน่วยงานที่รับผิดชอบโดยอัตโนมัติตามประเภทเรื่อง

### FR-04: การส่งต่อหน่วยงาน
- **FR-04-1** เจ้าหน้าที่สามารถส่งต่อเรื่องไปยังหน่วยงานที่รับผิดชอบได้
- **FR-04-2** การส่งต่อต้องบันทึก: หน่วยงานผู้ส่ง, หน่วยงานผู้รับ, วันที่, หมายเหตุ
- **FR-04-3** เรื่องสามารถส่งต่อได้หลายครั้ง (ประวัติการส่งต่อต้องครบถ้วน)
- **FR-04-4** หน่วยงานที่รับเรื่องต้องกด "รับเรื่อง" เพื่อเปลี่ยนสถานะ

### FR-05: การติดตามสถานะ
- **FR-05-1** สถานะเรื่องต้องเปลี่ยนแปลงตาม Workflow ที่กำหนด (ดูหัวข้อ Status Flow)
- **FR-05-2** ทุกการเปลี่ยนแปลงสถานะต้องบันทึก: ผู้กระทำ, เวลา, สถานะก่อน/หลัง, หมายเหตุ
- **FR-05-3** ประชาชนสามารถตรวจสอบสถานะผ่านหมายเลขเรื่องและรหัสติดตาม (Tracking Code)

### FR-06: SLA และการแจ้งเตือน
- **FR-06-1** ระบบต้องคำนวณวันครบกำหนดอัตโนมัติจากวันที่รับเรื่องและ SLA ของประเภทนั้น
- **FR-06-2** ระบบแจ้งเตือนภายใน (In-app Notification) เมื่อเรื่องเหลือเวลาน้อยกว่า 2 วัน
- **FR-06-3** ระบบแจ้งเตือนภายในเมื่อเรื่องเกินกำหนด (Overdue)
- **FR-06-4** รายการแจ้งเตือนต้องมีสถานะ อ่านแล้ว / ยังไม่ได้อ่าน

### FR-07: การบันทึกความคืบหน้าและผลการดำเนินการ
- **FR-07-1** เจ้าหน้าที่สามารถบันทึก Progress Note พร้อมวันที่ได้ทุกเมื่อ
- **FR-07-2** รองรับการแนบไฟล์ผลการดำเนินการ (เช่น หนังสือตอบกลับ, รูปภาพ)
- **FR-07-3** บันทึกหมายเหตุภายใน (Internal Note) ที่ประชาชนมองไม่เห็น

### FR-08: การปิดเรื่องและประเมินผล
- **FR-08-1** ผู้บริหาร/หัวหน้างานเป็นผู้ปิดเรื่องหลังตรวจสอบผลการดำเนินการ
- **FR-08-2** ระบบต้องบันทึกเหตุผลการปิดเรื่องหรือการยกเลิก

### FR-09: Dashboard และรายงาน
- **FR-09-1** แสดงจำนวนเรื่องแยกตามสถานะแบบ Real-time
- **FR-09-2** แสดงสถิติรายวัน / รายเดือน / รายปี
- **FR-09-3** แสดงรายการเรื่องที่เกินกำหนดและใกล้กำหนด
- **FR-09-4** แสดงสถิติแยกตามประเภทเรื่องและหน่วยงาน
- **FR-09-5** สามารถกรองข้อมูลตามช่วงวันที่, ประเภท, หน่วยงาน, สถานะ

### FR-10: การจัดการผู้ใช้และสิทธิ์ (Super Admin)
- **FR-10-1** สร้าง, แก้ไข, ระงับ, ลบบัญชีผู้ใช้งาน
- **FR-10-2** กำหนด Role ให้แต่ละบัญชี
- **FR-10-3** จัดการรายชื่อหน่วยงาน (Agency Management)
- **FR-10-4** จัดการประเภทเรื่องร้องเรียนและ SLA
- **FR-10-5** ดู Audit Log ของการกระทำสำคัญในระบบ

## 5. Non-Functional Requirements

| หมวด | รายละเอียด | ระดับความสำคัญ |
|---|---|---|
| **ภาษาไทย** | รองรับการแสดงผลและจัดเก็บภาษาไทยอย่างสมบูรณ์ (UTF-8 / utf8mb4) | สูงมาก |
| **ความปลอดภัย** | JWT Auth, Role-based Access, bcrypt password hashing | สูงมาก |
| **ประสิทธิภาพ** | หน้า Dashboard โหลดเสร็จใน < 3 วินาที | สูง |
| **Availability** | ระบบพร้อมใช้งานในเวลาราชการ (06.00–22.00 น.) | สูง |
| **Scalability** | รองรับผู้ใช้พร้อมกัน 50+ คนในเวอร์ชันแรก | ปานกลาง |
| **Data Integrity** | ข้อมูลต้องไม่สูญหาย มี Transaction Rollback | สูงมาก |
| **Audit Trail** | บันทึกการกระทำสำคัญทุกรายการพร้อม Timestamp | สูง |
| **Responsive Design** | ใช้งานได้บน Desktop และ Tablet (ไม่บังคับ Mobile) | ปานกลาง |
| **Maintainability** | โค้ดมีโครงสร้างชัดเจน, มี Comment ส่วนสำคัญ | สูง |

## 6. ข้อมูลที่ระบบต้องจัดเก็บ

### 6.1 ข้อมูลเรื่องร้องเรียน (Complaint)
- หมายเลขเรื่อง (Auto-generated), รหัสติดตาม (Tracking Code)
- วันที่รับเรื่อง, ช่องทางที่รับเรื่อง
- ประเภทเรื่อง (Category), ระดับความเร่งด่วน
- รายละเอียดเรื่องร้องเรียน (ภาษาไทย)
- สถานที่เกิดเหตุ (ถ้ามี)
- สถานะปัจจุบัน, วันครบกำหนด (Due Date)
- เจ้าหน้าที่ที่รับผิดชอบ, หน่วยงานที่รับผิดชอบ
- ไฟล์แนบ (Attachment)

### 6.2 ข้อมูลผู้ร้องเรียน (Complainant)
- ชื่อ-นามสกุล, เลขบัตรประชาชน (13 หลัก)
- ที่อยู่ (บ้านเลขที่, หมู่, ตำบล, อำเภอ)
- เบอร์โทรศัพท์, อีเมล (ถ้ามี)
- สถานะผู้ร้อง (ไม่ประสงค์ออกนาม หรือระบุตัวตน)

### 6.3 ประวัติการเปลี่ยนแปลงสถานะ (Status History)
- สถานะก่อนเปลี่ยน, สถานะหลังเปลี่ยน
- ผู้ที่เปลี่ยน, วันเวลาที่เปลี่ยน, หมายเหตุ

### 6.4 ประวัติการส่งต่อ (Forward History)
- หน่วยงานผู้ส่ง, หน่วยงานผู้รับ
- ผู้ที่สั่งส่งต่อ, วันเวลา, หมายเหตุ

### 6.5 บันทึกความคืบหน้า (Progress Notes)
- ผู้บันทึก, วันเวลา, เนื้อหา, ไฟล์แนบ, ประเภท (Internal/Public)

### 6.6 การแจ้งเตือน (Notifications)
- ผู้รับ, ประเภทการแจ้งเตือน, เนื้อหา, สถานะ (อ่านแล้ว/ยังไม่อ่าน), วันเวลา

### 6.7 ข้อมูลผู้ใช้ระบบ (Users)
- ชื่อ-นามสกุล, Username, Password (Hashed), Role, หน่วยงาน, สถานะ

### 6.8 ข้อมูลหน่วยงาน (Agencies)
- ชื่อหน่วยงาน, รหัสหน่วยงาน, ประเภท (ภายใน/ภายนอก), ผู้ประสานงาน

### 6.9 ประเภทเรื่องร้องเรียน (Categories)
- ชื่อประเภท, คำอธิบาย, SLA เริ่มต้น (วัน), หน่วยงานที่รับผิดชอบ, สถานะ (เปิด/ปิด)

### 6.10 Audit Log
- ผู้กระทำ, Action, รายละเอียด, IP Address, Timestamp

## 7. ข้อมูลที่ระบบต้องแสดงผล

### 7.1 หน้าสำหรับประชาชน (Public)
- **แบบฟอร์มยื่นเรื่อง:** Fields ทั้งหมดพร้อม Validation, เลือกประเภท, แนบไฟล์
- **หน้าติดตามสถานะ:** ป้อนหมายเลขเรื่อง + Tracking Code → แสดง Timeline ของสถานะ

### 7.2 หน้าสำหรับเจ้าหน้าที่รับเรื่อง (Officer)
- รายการเรื่องทั้งหมดที่รับผิดชอบ (พร้อม Filter/Search)
- รายละเอียดเรื่องร้องเรียน (ทุก Field + ประวัติ)
- ปุ่มเปลี่ยนสถานะ, ส่งต่อหน่วยงาน, บันทึก Progress Note

### 7.3 หน้าสำหรับผู้บริหาร (Admin/Supervisor)
- Dashboard: สถิติ Real-time, กราฟ, รายการ Overdue
- รายงานที่กรองตามเงื่อนไขต่างๆ ได้

### 7.4 หน้า Notification
- รายการแจ้งเตือนทั้งหมด, สถานะ อ่าน/ยังไม่อ่าน, ลิงก์ไปยังเรื่องที่แจ้งเตือน

## 8. เงื่อนไขทางธุรกิจของระบบ (Business Rules)

| รหัส | เงื่อนไข |
|---|---|
| **BR-01** | หมายเลขเรื่องต้องไม่ซ้ำกันและสร้างอัตโนมัติในรูปแบบ: `DCMS-YYYY-NNNNNN` |
| **BR-02** | Tracking Code สำหรับประชาชนต้องเป็น Random String ที่คาดเดาได้ยาก |
| **BR-03** | เรื่องที่สถานะ `CLOSED` หรือ `CANCELLED` ต้องไม่สามารถแก้ไขสถานะได้อีก |
| **BR-04** | เฉพาะเจ้าหน้าที่ที่รับผิดชอบหรือ Admin เท่านั้นที่เปลี่ยนสถานะเรื่องได้ |
| **BR-05** | การส่งต่อต้องระบุหน่วยงานปลายทางและหมายเหตุทุกครั้ง |
| **BR-06** | ระบบคำนวณ Due Date โดย: `Due Date = วันที่รับเรื่อง + SLA (วัน) (ไม่นับวันหยุดราชการ)` |
| **BR-07** | เรื่องที่รับมาจากประชาชนออนไลน์ต้องมีเจ้าหน้าที่ "รับเรื่อง" ก่อนจึงจะเปลี่ยนสถานะได้ |
| **BR-08** | ไฟล์แนบต้องไม่เกิน 10 MB ต่อไฟล์ และรองรับเฉพาะ: `.pdf`, `.jpg`, `.jpeg`, `.png`, `.docx` |
| **BR-09** | ผู้ร้องที่ไม่ประสงค์ออกนามจะไม่ถูกแสดงชื่อในหน้าสาธารณะ |
| **BR-10** | Audit Log ต้องบันทึกทุกการเปลี่ยนแปลงสำคัญ (เปลี่ยนสถานะ, ส่งต่อ, แก้ไขข้อมูล) |

## 9. ข้อจำกัดและข้อควรระวัง

### 9.1 ข้อจำกัดทางเทคนิค
- **Ephemeral Filesystem บน Railway:** ไฟล์แนบที่เก็บใน Container จะหายเมื่อ Deploy ใหม่ ต้องใช้ Railway Volume หรือ Object Storage ภายนอก (เช่น AWS S3, Cloudflare R2) ในอนาคต
- **เวอร์ชันแรกไม่มี Email/SMS จริง:** ใช้ระบบแจ้งเตือนภายใน (In-app) เท่านั้น
- **ไม่มี Mobile App:** รองรับ Browser เป็นหลัก (Responsive Web Design)

### 9.2 ข้อควรระวังด้านความปลอดภัย
- เลขบัตรประชาชนเป็นข้อมูลส่วนบุคคลชั้น 2 ต้องจัดการด้วยความระมัดระวัง
- ต้องมีการตรวจสอบ Input Validation ทั้ง Frontend และ Backend
- ต้องมีการป้องกัน SQL Injection ด้วย Parameterized Queries เสมอ

### 9.3 ข้อจำกัดทางธุรกิจ
- ระยะเวลา SLA อาจต้องสอดคล้องกับระเบียบราชการ (เช่น ภายใน 15 วันทำการ)
- บางประเภทเรื่องอาจไม่อยู่ในอำนาจของจังหวัด ต้องมีกระบวนการ "ส่งคืน/ยกเลิก" ที่ชัดเจน
