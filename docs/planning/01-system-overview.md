# 01 — System Overview
## ระบบรับเรื่องร้องเรียนศูนย์ดำรงธรรมจังหวัดศรีสะเกษ (DCMS)

> **Planning Only** — ห้ามเขียน Code จนกว่า Implementation Plan จะได้รับการอนุมัติ

---

## 1. ชื่อและความเป็นมาของระบบ

| รายการ | รายละเอียด |
|---|---|
| **ชื่อระบบ** | ระบบรับเรื่องร้องเรียนศูนย์ดำรงธรรมจังหวัดศรีสะเกษ |
| **ชื่อย่อ** | DCMS (Damrongdham Center Management System) |
| **หน่วยงานเจ้าของ** | ศูนย์ดำรงธรรมจังหวัดศรีสะเกษ |
| **วัตถุประสงค์** | พัฒนาระบบดิจิทัลสำหรับรับ ติดตาม และจัดการเรื่องร้องเรียนของประชาชน |

ศูนย์ดำรงธรรมจังหวัดศรีสะเกษเป็นหน่วยงานที่มีบทบาทหลักในการรับเรื่องราวร้องทุกข์ ร้องเรียน และการขอความเป็นธรรมจากประชาชน ปัจจุบันกระบวนการหลายขั้นตอนยังคงอยู่ในรูปแบบเอกสารกระดาษและการบันทึกด้วยมือ ซึ่งทำให้การติดตามสถานะ การส่งต่อหน่วยงาน และการรายงานผลต่อผู้บริหารทำได้ล่าช้าและไม่มีประสิทธิภาพ

---

## 2. เป้าหมายหลักของระบบ

1. **เพิ่มประสิทธิภาพการรับเรื่อง:** บันทึกข้อมูลเรื่องร้องเรียนแบบดิจิทัลให้สมบูรณ์และเป็นมาตรฐาน
2. **ลดระยะเวลาดำเนินการ:** กำหนด SLA (ระยะเวลาดำเนินการ) และแจ้งเตือนเมื่อใกล้ถึงกำหนด
3. **เพิ่มความโปร่งใส:** ประชาชนและเจ้าหน้าที่สามารถติดตามสถานะเรื่องร้องเรียนได้ตลอดเวลา
4. **ส่งต่อได้อย่างรวดเร็ว:** ระบบช่วยส่งเรื่องไปยังหน่วยงานที่รับผิดชอบและบันทึกประวัติการส่งต่อ
5. **ข้อมูลสำหรับผู้บริหาร:** Dashboard แสดงภาพรวมสถิติและสถานะแบบ Real-time

---

## 3. ผู้ใช้งานหลัก (Target Users)

| กลุ่มผู้ใช้ | หน้าที่หลัก |
|---|---|
| **ประชาชน (Citizen)** | ยื่นเรื่องร้องเรียนออนไลน์, ติดตามสถานะ |
| **เจ้าหน้าที่รับเรื่อง (Officer)** | รับเรื่อง, บันทึกข้อมูล, ส่งต่อหน่วยงาน, อัปเดตสถานะ |
| **เจ้าหน้าที่หน่วยงาน (Agency Officer)** | รับงานที่ส่งต่อมา, อัปเดตความคืบหน้า, แนบผลการดำเนินการ |
| **ผู้บริหาร / หัวหน้างาน (Admin/Supervisor)** | ดู Dashboard, ออกรายงาน, ติดตามภาพรวม, กำหนดหน่วยงาน |
| **ผู้ดูแลระบบ (Super Admin)** | จัดการผู้ใช้ทั้งหมด, ตั้งค่าระบบ |

## 4. ขอบเขตของระบบ (System Scope)

### ✅ อยู่ในขอบเขต (In Scope)
- การรับและบันทึกเรื่องร้องเรียนแบบออนไลน์
- การจำแนกประเภทเรื่องร้องเรียน
- การส่งต่อเรื่องไปยังหน่วยงานที่รับผิดชอบ
- การติดตามสถานะตลอดกระบวนการ
- การแจ้งเตือน (Notification) ผ่านระบบ
- Dashboard สำหรับผู้บริหาร
- การออกรายงานสรุป
- ระบบ Authentication และ Role-based Access Control

### ❌ อยู่นอกขอบเขต (Out of Scope) — เวอร์ชันแรก
- การแจ้งเตือนผ่าน SMS หรือ Email จริง (ใช้ระบบ Notification ภายในก่อน)
- การรับเรื่องผ่าน LINE OA หรือช่องทาง Social Media
- การชำระเงินหรือธุรกรรมทางการเงิน
- Mobile Application (iOS/Android) — อาจพัฒนาในอนาคต
- การเชื่อมต่อกับระบบราชการอื่นๆ (EGP, GLink)

## 5. ฟีเจอร์หลักของระบบ (Core Features)

### F01 — การรับและบันทึกเรื่องร้องเรียน
- ประชาชนสามารถยื่นเรื่องร้องเรียนออนไลน์ได้โดยไม่ต้องลงทะเบียนสมาชิก
- กรอกข้อมูลผู้ร้อง, ประเภทเรื่อง, รายละเอียด, แนบไฟล์หลักฐาน
- ระบบออกเลขรับเรื่องอัตโนมัติและเป็นเอกลักษณ์
- ผู้ร้องได้รับรหัสสำหรับติดตามสถานะ

### F02 — การจำแนกประเภทเรื่องร้องเรียน
- จัดหมวดหมู่เรื่องร้องเรียนตามประเภท (เช่น ที่ดิน, น้ำ, สาธารณูปโภค, การทุจริต ฯลฯ)
- ระบุระดับความเร่งด่วน
- กำหนดหน่วยงานที่รับผิดชอบเบื้องต้นอัตโนมัติตามประเภท

### F03 — การส่งต่อหน่วยงาน
- เจ้าหน้าที่สามารถส่งต่อเรื่องไปยังหน่วยงานภายในหรือภายนอกได้
- บันทึกประวัติการส่งต่อทั้งหมด
- หน่วยงานปลายทางได้รับการแจ้งเตือนทันที

### F04 — การติดตามสถานะ
- สถานะของเรื่องร้องเรียนเปลี่ยนแปลงตามขั้นตอนการดำเนินงาน
- ทุกการเปลี่ยนแปลงสถานะถูกบันทึกพร้อมเวลาและผู้ดำเนินการ
- ประชาชนตรวจสอบสถานะผ่านหมายเลขเรื่องและรหัสได้

### F05 — การกำหนดระยะเวลาและการแจ้งเตือน SLA
- กำหนดระยะเวลาดำเนินการสูงสุดตามประเภทเรื่อง
- แจ้งเตือนเจ้าหน้าที่เมื่อเรื่องใกล้ครบกำหนด
- แจ้งเตือนเมื่อเรื่องเกินกำหนด (Overdue)

### F06 — การบันทึกผลการดำเนินการ
- เจ้าหน้าที่บันทึกความคืบหน้าและผลการดำเนินการ
- แนบไฟล์เอกสารผลการดำเนินการ
- บันทึกหมายเหตุภายในของเจ้าหน้าที่

### F07 — Dashboard และรายงาน
- แสดงจำนวนเรื่องตามสถานะ, ประเภท, หน่วยงาน
- สถิติรายวัน/รายสัปดาห์/รายเดือน
- เรื่องที่เกินกำหนดและใกล้กำหนด
- ออกรายงานสรุปในรูปแบบที่กำหนด

### F08 — การจัดการผู้ใช้และสิทธิ์
- สร้าง, แก้ไข, ระงับบัญชีผู้ใช้งาน
- กำหนด Role และ Permission
- บันทึก Audit Log ของการกระทำสำคัญในระบบ

## 6. สถานะของเรื่องร้องเรียน (Complaint Status Flow)

```text
[รับเรื่อง] 
    ↓
[กำลังพิจารณา] 
    ↓
[ส่งต่อหน่วยงาน] ←→ [รับงานโดยหน่วยงาน]
    ↓
[อยู่ระหว่างดำเนินการ]
    ↓
[ดำเนินการแล้ว / รอตรวจสอบ]
    ↓
[ปิดเรื่อง / เสร็จสิ้น]
    ↓  
[ยกเลิก / ไม่อยู่ในอำนาจ] (กรณีพิเศษ)
```

| สถานะ | ความหมาย |
|---|---|
| `PENDING` | รับเรื่องแล้ว รอเจ้าหน้าที่พิจารณา |
| `IN_REVIEW` | เจ้าหน้าที่กำลังพิจารณา |
| `FORWARDED` | ส่งต่อหน่วยงานแล้ว |
| `IN_PROGRESS` | หน่วยงานรับเรื่องและกำลังดำเนินการ |
| `RESOLVED` | ดำเนินการเสร็จสิ้น รอผู้บริหารตรวจสอบ |
| `CLOSED` | ปิดเรื่องสมบูรณ์ |
| `CANCELLED` | ยกเลิกเรื่อง (ไม่อยู่ในอำนาจ / ข้อมูลไม่ครบ) |

## 7. Tech Stack ที่เลือกใช้

| ส่วน | เทคโนโลยี | เหตุผล |
|---|---|---|
| Frontend | React 18 + Vite 5 + MUI 5 | Modern UI, Hot Reload เร็ว, Component Library ครบ |
| Backend | Node.js 20 LTS + Express 4 | เสถียร, Ecosystem กว้าง, เหมาะกับ REST API |
| Database | MySQL 8 | Relational DB, รองรับภาษาไทย (utf8mb4), มีความน่าเชื่อถือ |
| Container Dev | Docker Compose + phpMyAdmin | มาตรฐานเดียวกันในทีม, ง่ายต่อการตั้งค่า |
| Deployment | Railway (Dockerfile multi-stage) | PaaS ที่ใช้ง่าย, จัดการ SSL/Domain อัตโนมัติ |

## 8. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน (Non-Functional Requirements)

| หมวด | ข้อกำหนด |
|---|---|
| **ภาษา** | รองรับภาษาไทยอย่างสมบูรณ์ (ชื่อ-นามสกุล, เนื้อหาร้องเรียน, รายงาน) |
| **ความปลอดภัย** | JWT Authentication, Role-based Access, Password Hashing (bcrypt) |
| **Availability** | ควรพร้อมใช้งานในเวลาราชการ (06.00–20.00 น.) |
| **Scalability** | รองรับ Concurrent Users เบื้องต้นได้ (ไม่น้อยกว่า 50 คน) |
| **Maintainability** | โค้ดต้องมี Comment อธิบายส่วนสำคัญ, โครงสร้างชัดเจน |
| **Data Integrity** | ข้อมูลร้องเรียนต้องไม่สูญหายและมี Audit Log |

## 9. ข้อจำกัดและสมมติฐาน (Constraints & Assumptions)

### ข้อจำกัด
- Deployment บน Railway มี Ephemeral Filesystem: ไฟล์แนบต้องใช้ Railway Volume หรือ Object Storage ในอนาคต
- เวอร์ชันแรกยังไม่รองรับการส่ง Email/SMS จริง

### สมมติฐาน
- มีเจ้าหน้าที่ (Admin) ที่จะบริหารจัดการระบบเบื้องต้นได้
- ผู้ใช้มีอุปกรณ์และการเชื่อมต่ออินเทอร์เน็ตขั้นพื้นฐาน
- การยืนยันตัวตนของประชาชนใช้ชื่อ-นามสกุลและเลขบัตรประชาชน (ไม่ได้ผ่าน Digital ID ภายนอก)

## 11. สรุปภาพรวมสถาปัตยกรรม

```text
[Browser / ประชาชน / เจ้าหน้าที่ / ผู้บริหาร]
        ↓ HTTPS
[Frontend: React 18 + Vite 5 + MUI 5 (Port 5173 Dev)]
        ↓ REST API (JSON)
[Backend: Node.js 20 + Express 4 (Port 5001)]
        ↓
[Database: MySQL 8 (Port 3306 internal / 3307 host)]
```

**Development Environment:**
- ทุก Service รันผ่าน Docker Compose
- phpMyAdmin สำหรับจัดการ Database (Port 8081)
- Hot Reload ทั้ง Frontend (Vite HMR) และ Backend (nodemon)

**Production Environment:**
- Single-container บน Railway จาก Dockerfile multi-stage
- Railway จัดการ SSL/Domain อัตโนมัติ
- ไม่ใช้ Nginx แยก
